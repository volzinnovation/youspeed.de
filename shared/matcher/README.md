# Native matcher conformance

The Phase 1 candidate-admission fixture is consumed by real Swift/SQLite and
Android/SQLite tests. It exercises the bounds-only fallback, general R-tree and
network-specific R-tree paths with the same data and expected capped candidates.

Admission is performed separately for each queried network. Spatial bounds
filter eligible rows; the existing Android squared distance from the GPS point
to the **way bounding box in degrees** orders them before the per-network cap.
This is a coarse admission heuristic, not a geodesic distance or final score.
Equal distances are ordered by `CAST(w.way_id AS TEXT) COLLATE BINARY ASC`.
The final geometry, heading and continuity scorers retain their existing logic.

Previously iPhone applied `LIMIT` without an order. In a dense query the nearest
road could be omitted depending on row insertion order or query plan. Android
already ordered by bounding-box proximity but did not define ties. Both now
use the same deterministic admission contract. Candidate *sets* below the cap
remain unchanged; capped queries and previously unspecified equal-score order
are explicitly covered by this correction.

The fixture includes a 64-bit way ID above 2^53 and a `10`/`2` lexical tie to
detect accidental floating-point ID conversion or numeric/text ordering drift.
Both native suites also check M7–M12 lookup results against the same expected
nearest way and speed, repeatedly using the retained connection.

These synthetic fixtures complement the existing native junction, continuity,
tunnel and sequence tests. They do not establish on-road accuracy or change the
governed speed-limit-reference policy.

`sequence-v1.json` adds 13 shared context/history decisions over the SQL in
`fixtures/`: linked and unlinked turns, motion/history inference, route and
street continuity, and tunnel entry/recovery. Each native test runs every case
cold and twice warm. These fixtures are the former Android matcher test assets;
existing platform-specific regressions remain alongside the common corpus.

Android system SQLite builds do not always provide the R-tree module. Test
fixture creation explicitly logs when it substitutes ordinary bounds tables;
that exercises SQL shape/admission but is not native R-tree coverage. The
separate `NativeRtreeFallbackInstrumentedTest` uses an unchanged real R-tree
SQLite file, generated by `scripts/map/tests/generate_android_rtree_fixture.py`,
and verifies production lookup plus unchanged file bytes. It records whether
the native module or production bounds fallback was actually used. iPhone's
candidate tests create real R-tree virtual tables.
